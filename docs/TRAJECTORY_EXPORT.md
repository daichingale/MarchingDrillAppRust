# Count-accurate trajectory CSV (read-only export)

This is an independent DrillForge interchange/inspection format, not a Pyware
file format or a claim of interoperability with proprietary Pyware projects.

## From the desktop editor

1. Select at least one performer on the 2D field.
2. Navigate to a set that has a following set.
3. In the timeline options choose **軌跡CSVを書き出す / Export trajectory CSV**.
4. Choose a destination. The existing asynchronous text writer writes the CSV.

Unlike the ordinary *Scene coordinates* button, this export samples every integer
count for the **current set to the next set**, including curve, arc, path, easing,
per-performer gates and holds. It is read-only, does not alter the show or
Undo/Redo history, and is generated by the core playback evaluator.

## Columns and coordinate conventions

```csv
from_set,to_set,local_count,global_count,phase,performer,label,x,y,unit
```

- `from_set` / `to_set`: actual user-facing set names, CSV-quoted.
- `local_count`: zero-based count relative to `from_set`, starting at 0.
- `global_count`: zero-based show count including earlier holds.
- `phase`: `move` before the source set's arrival count; `arrival` at
  exactly the source set's movement-count boundary; `hold` for any subsequent
  source-set hold counts.
- `performer`: stable performer ID; `label`: the roster label.
- `x` / `y`: numeric coordinates in the document's field coordinate system,
  printed to six decimals. The convention is `y = 0` at the front edge.
- `unit`: either `meters` or `yards` based on the document grid.

The export includes both endpoints (0 and movement count), and any intermediate
hold counts, but does **not** append another row for the following set's next
transition. A stationary/gated performer may have identical coordinates at
successive counts. The output order is count-major, then selected-performer
order; it is deterministic for the same input.

The writer emits UTF-8; spreadsheet software may need explicit UTF-8 import.
The data contains six-decimal field coordinates for interchange/inspection,
not a metric-precision or body-position guarantee. No proprietary vendor
assets or file parsers are used.

## Limits and verification

- At most `MAX_TRAJECTORY_CSV_ROWS = 50,000` body rows may be requested;
  larger requests return `TooManyRows` rather than stalling the UI with a
  giant clipboard payload.
- Invalid / duplicate performer indices, empty selection and missing next
  set are rejected without changing the project.
- The core tests cover arrival/hold inclusion, a gated curved route
  matching the same live playback evaluator, escaping and unit labeling,
  and error cases. Hardware/UI acceptance still requires Windows/macOS
  smoke tests.
