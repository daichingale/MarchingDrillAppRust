# DrillForge 設計規約（全設計文書の共通前提）

この文書は `docs/design/` 配下の各設計文書が従う共通ルールを定める。
各設計文書の執筆者（人・エージェント問わず）は、着手前にこの文書と
[DESIGN_GAPS.md](../../DESIGN_GAPS.md) / [ARCHITECTURE.md](../../ARCHITECTURE.md) /
[PRODUCT_QUALITY.md](../../PRODUCT_QUALITY.md) / [MEDIA_PIPELINE.md](../../MEDIA_PIPELINE.md) を読むこと。

## 製品目標

**販売可能な水準の、安全で高性能なマーチングドリル制作環境。Pyware 3D の上位互換。**

「上位互換」の定義:

- Pyware 3D で出来ることは全て出来る（機能の網羅）
- そのうえで、速度・発見性・解析・自動化・出力品質で明確に上回る
- **模倣しないもの**: Pyware の商標、UI の意匠、同梱アセット、独自ファイル形式の内部仕様の複製。
  相互運用は「利用者が所有するデータ」または「公開された仕様」に基づく独立実装としてのみ行う。
  この境界は `ARCHITECTURE.md` の決定であり、設計文書はこれを覆さない。

## 言語

| 対象 | 言語 |
|---|---|
| 設計文書・UI文字列・ユーザー向けテキスト | 日本語 |
| Rust の識別子・doc comment・コード内コメント | 英語 |
| コミットメッセージ | 英語 |

`drill-core` の中に日本語文字列リテラルを置かない（`Locale` 経由で解決する）。これは既存の技術的負債であり、
新しい設計で再発させない。

## クレート境界

```
drill-core    ドキュメントモデル・時間・座標・解析・保存検証。依存は serde/serde_json のみ。
              UI・GPU・OS・音声デバイス・ファイルダイアログを知らない。純粋ロジック。
drill-render  DisplayList 中間表現とその生成。drill-core にのみ依存。描画APIを知らない。
drill-audio   デコード・再生・波形。symphonia/cpal。drill-core に依存。
drill-export  SVG/PNG/PDF/動画/CSV。drill-render に依存。
drill-app     egui/wgpu の表示と入力変換のみ。業務ロジックを持たない。
```

新しいクレートを提案する場合は、この表のどこに入るかと依存方向を明示すること。依存は必ず上から下へ。

## 全設計に共通する不変条件

これらに違反する設計は却下される。

1. `Document` の変更は必ず `Edit` コマンドを通る。UI から直接フィールドを書き換えない。
2. セットや演者の**同一性は安定ID**（`SetId` / `PerformerId`）、**順序は Vec の索引**。両者を混同する API を作らない。
3. 毎フレーム走る関数は `&mut` の作業領域（scratch）を受け取り、内部でヒープ確保しない。
4. 音声時刻は**サンプル索引**、映像時刻は**有理数フレーム時刻**。浮動小数の累加で時間を進めない。
5. 同じ `(Document, config, count)` からは常に同じ出力（DisplayList・フレーム・座標表）が出る。決定論。
6. UI スレッドでデコード・フレーム描画・エンコード・全文書スキャンを行わない。
7. 人間可読テキストを返す関数は `Locale` を引数に取る。
8. 公開 API は `Result<_, DrillError>` を返す。`Result<_, String>` を新規に作らない。

## 性能予算

`PRODUCT_QUALITY.md` の数値を全設計が共有する。設計文書は自分の担当範囲について、
この予算のうち**何ミリ秒を使うか**を明示すること。

- 基準規模: **演者1,000人 / セット64 / 総カウント2,048**
- 入力から描画まで **16.6ms**（60fps）
- 通常編集の Undo/Redo **2ms 未満**
- 再生中のフレーム内ヒープ確保 **ゼロ**
- 2時間連続再生で常駐メモリの継続増加なし

上限規模（劣化してよいが壊れてはいけない）: 演者4,000人 / セット256。

## 安全性（「売れる」ための必須要件）

設計文書は該当する範囲について次を必ず扱うこと。

- **信頼できない入力**: 他人から受け取ったプロジェクトファイル・音源・インポート元ファイルは全て敵性入力として扱う。
  サイズ上限、要素数上限、再帰深度上限、NaN/Inf 拒否、パス・トラバーサル拒否。
- **パニック禁止経路**: ファイル読込・インポート・デコードで `unwrap` / `expect` / 添字パニック / 整数オーバーフローを起こさない。
- **データ喪失防止**: 上書きは原子的置換（temp へ書いて rename）。失敗時に元ファイルを壊さない。
- **プロセス分離**: 外部プロセス（FFmpeg）は引数配列で起動する。シェル文字列を組み立てない。
- **プライバシー**: 既定でテレメトリを送らない。クラッシュレポートは送信前に内容を利用者へ提示する。

## 各設計文書の構成（必ずこの見出しで書く）

```markdown
# <番号>. <題名>

## 1. 目的と範囲
何を解決するか。この文書が扱わないことも明記する。

## 2. 現状
リポジトリの現在のコードで何が有り、何が無いか。ファイル名と行番号で示す。推測で書かない。

## 3. 設計
実際に書ける Rust の型・トレイト・関数シグネチャ。アルゴリズムと計算量。
「〜のようなものを用意する」ではなく、コンパイル可能な粒度で書く。

## 4. 不変条件
この設計が守る性質。テストで検証できる形で書く。

## 5. 性能
基準規模での想定コストと、16.6ms 予算のうちの取り分。計算量とメモリ量。

## 6. 失敗モードと安全性
壊れ方の列挙と、それぞれへの対処。信頼できない入力の扱い。

## 7. テスト計画
単体・ゴールデン・property・ストレス・ベンチの具体的な項目。

## 8. 実装タスク
Codex に渡せる粒度（1タスク = 1〜3時間相当）へ分解し、依存関係と並行可能性を示す。

## 9. 未決事項
判断を保留した点と、決めるために必要な情報。
```

## 執筆時の禁止事項

- 既存コードを読まずに「現状」を書くこと
- 動かないコード片（型が合わない、存在しない API を呼ぶ）を設計に載せること
- 他の設計文書の担当範囲へ踏み込んで別の設計を与えること（境界で参照するのは可）
- リポジトリのソースコードを変更すること（設計文書の執筆者はコードを書かない）
